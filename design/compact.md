Context compaction should be designed as **state transfer for continuing an agent task**, not as ordinary conversation summarization. The objective is not to produce a readable recap, but to create the smallest context from which the agent can continue almost as if the removed history were still available. Current systems such as Claude and OpenAI use this general model: older context is replaced by a compact representation and execution continues from that representation.

A good default architecture is **compressed history + a verbatim recent tail**. Do not summarize the entire session every time. Preserve the latest few logical turns, including their tool calls and results, without modification, and compact the older prefix. This is increasingly common in production agent frameworks and is important because recent interactions contain the immediate execution state. A 2026 study of agent compaction found that compression can weaken the effect of recent interactions and lead to repeated exploration or incorrect actions, which makes preserving the active tail especially valuable.

The compacted state should prioritize information required for future actions: the user's original objective and current subtask; explicit constraints and preferences; decisions already made and why they matter; facts established from web pages; relevant URLs, identifiers, exact values and names; actions already performed; important failures and why they failed; unresolved questions; and the next likely actions. For a web agent, large HTML dumps, screenshots, repeated search results, intermediate reasoning, unsuccessful exploration with no future relevance, and verbose tool logs should normally disappear. Preserve the **result of a tool interaction**, not its raw output, unless exact content is needed later. This matches production guidance that compaction should preserve decisions, unresolved issues and implementation/task state while aggressively removing redundant tool output.

Be careful with browser state. Distinguish durable information from ephemeral execution state. URLs, information extracted from a page, submitted form values, selected options, and completed actions may be worth retaining. DOM node IDs, temporary element handles, stale tab indexes, transient loading state, and similar identifiers should only be kept when the runtime guarantees they remain valid. Compaction itself should not invoke tools, modify memory, or update chat-history storage; it should be a pure transformation of the supplied session transcript into continuation state. This also avoids a real failure mode seen in tool-enabled compaction APIs where the model tries to call a tool instead of producing the summary.

Trigger compaction according to **token pressure**, not simply every N messages. Leave enough headroom for the compaction operation itself and for subsequent model output/tool interactions. It can also be useful to compact at natural task boundaries—after completing a search phase, establishing a root cause, or finishing a subtask—because obsolete exploration can then be discarded cleanly. Very long contexts can hurt agent behaviour well before the formal context-window limit; recent research on long-horizon search reports premature termination and degraded behaviour as irrelevant history accumulates.

Compaction is inherently lossy, so repeated compactions need particular care. Avoid repeatedly paraphrasing important facts into increasingly vague prose. Use a relatively stable structure and preserve exact strings where precision matters. Clearly distinguish facts observed from tools, user-provided requirements, agent decisions, hypotheses, and unresolved uncertainty. New compaction should merge the previous compacted state with newly expired turns rather than treating everything as equally important. Recent research also suggests that summary length and retained information can vary considerably between runs, so the implementation should enforce an approximate token budget and evaluate whether critical state survives rather than trusting the summarizer to choose an appropriate length automatically.

Finally, evaluate compaction by **continuation quality**, not summary quality. A summary can look excellent to a human while causing the agent to repeat searches, forget a constraint, revisit a rejected approach, or take a wrong browser action. Tests should therefore snapshot the session immediately before compaction, continue equivalent tasks with the original and compacted contexts, and compare actions and task success. This “boundary-local” evaluation is also the direction of recent work on reliable agent compression.

In short, think of compaction as creating a compact **working checkpoint**: preserve actionable state and the recent execution frontier exactly, compress established history aggressively, remove bulky observations once their useful conclusions have been captured, and optimize for the agent's ability to continue rather than for the readability of the summary.
